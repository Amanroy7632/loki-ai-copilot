## Acceptance criteria
- [x] Exhaustive transition tests: all 8 states × 12 events, including rejected events leaving
  state unchanged (`every_state_event_pair_matches_the_transition_table`).
- [x] `Muted → Idle` happens only on Unmute: checked from every starting state after mute,
  with every other event attempted (`only_explicit_unmute_can_leave_muted_from_every_starting_state`).

## Known limitations
- Pure state transitions do not release devices or cancel futures. The runtime driver must
  perform these effects, serialize events, and discard old-session completions.
- `StartListening` represents a future explicitly enabled wake-word driver; no wake-word engine
  is implemented or enabled. `CleanupComplete` must follow actual cancellation cleanup.
- No CLI wiring, capture, STT, TTS or P3 integration is included. This worktree intentionally
  starts from the committed baseline rather than the uncommitted P3 snapshot.
- A source-hash comparison observed concurrent edits in the main P3 checkout during validation.
  Those edits were left alone; all implementation writes and builds here use the P4 worktree.

## Security implications
- Muted stays latched; unmute does not open capture. Speaking rejects capture events.
- Transcription is input, never authorization. There is no approval API in this module.
- No new network access, dependencies, stored data, IPC or OS capabilities.
- SEC-11 end-to-end verification remains part of later runtime integration, not claimed here.

## Decisions made
- No architecture or crate-graph change; no ADR required. The explicit listening and cleanup
  events fill the corresponding edges already present in the voice lifecycle diagram.
